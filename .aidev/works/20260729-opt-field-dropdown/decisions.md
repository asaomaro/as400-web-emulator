# 決定記録

## D1: UI はキーイベントを 1 つも購読しない（利用者指示への対応）

- 背景: 利用者から「**矩形選択やコピー＆ペーストに影響を与えないように**」との指示（2026-07-29）。
  spec の初版は `Esc` で閉じる・欄の右端に印を置いてクリックで開く、としていた。
- 実装を読んで確認した干渉点:
  - `@mousedown="onGridMousedown"` は**グリッド直下**にあり、`cellAt()` は座標から桁を算出する。
    **グリッド内のどこを押しても** `clearRectSel()` が走り矩形選択が消える
  - 貼り付けは入力欄の `@paste`。**フォーカスを奪うと貼り付け先が変わる**
  - コピー（`onDocCopy` → `rectText()`）は `charAtForClipboard`＝**モデル**から組むので、
    DOM にオーバーレイがあってもクリップボードには混入しない（この経路は安全）
- 決定:
  - **開閉はフォーカスにのみ従属**させる。キーイベントは 1 つも購読しない（`Esc` すら捕まえない）
  - ポップオーバーと項目に **`@mousedown.stop.prevent`**（伝播と既定のフォーカス移動を両方止める）
  - 選択は `click`。**グリッド内に導線（印）を置かない**
- 理由 / 代替案: `Esc` を捕まえると 5250 側のキー経路と競合しうる。印を置くと桁割りを侵し、
  mousedown のヒット領域も増える。**矩形選択が始まると `onGridDragMove` が入力欄を blur する**ので、
  フォーカス従属にしておくだけで選択開始と同時に自然に閉じる——余計な仕掛けが要らない。
- 影響: 開く操作が「Opt 欄にフォーカスする」だけになり、キーボードでの明示的な開閉は無い。
  設定 OFF が既定なので、ONにした利用者は出ることを期待している前提。

## D2: 選択の反映はフォーカス経路の `pasteFrom` を通す

- 背景: 当初 `pasteFrom(at, value)` を焦点文脈なしで呼んでいたが、テストで欄の値が入らなかった。
- 判明: `pasteFrom` は焦点文脈が無いと `emit("edit")` の非フォーカス経路へ落ち、
  親が edits を適用するまで DOM に反映されない。
- 決定: `pasteFrom({row,col}, value, { f, el, startOffset: 0 })` と**焦点文脈を渡す**。
- 理由: Opt 欄はフォーカス中なのだから、打鍵と同じ扱い（edit モデルの更新・`sync`）が正しい。
  渡さないとカーソルと編集状態が食い違う。
- 影響: なし（より正しい経路になった）。

## D3: 負のテストが規則を突けていなかった（空振り検証で判明）

- 背景: `wrkmsgq` / `menu` を「Opt 列が無ければ凡例があっても null」の根拠にしていた。
- **空振り検証で発覚**: Opt 列の条件を無効化しても 10/10 が通ってしまった。
  この 2 画面は**そもそも凡例が無い**ので、`options.length === 0` で null になっていただけ。
  「両方揃ったときだけ発火する」という規則そのものは**1 つもテストされていなかった**。
- 決定: 実機 PDM（凡例あり）から**入力欄だけを取り去った** snapshot と、
  **短い欄が 2 行しか並ばない** snapshot を足す。
- 効果: 条件を無効化すると**この 2 件が落ちる**ことを確認した。
- 教訓: 負のケースは「なぜ null になるのか」まで確かめないと、別の理由で通っているだけになる。
