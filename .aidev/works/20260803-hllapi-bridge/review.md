## ラウンド 1（2026-08-03）

### 要件との突き合わせ

| 指示 | 実現 |
|---|---|
| 「HLLAPI と EHLLAPI への対応」 | 標準の `hllapi(int*,char*,int*,int*)` で受け、20 機能に対応。別名 4 つ |
| 「**Rust で薄い接続層**」 | C ABI ↔ HTTP のみ。**機能番号の意味を 1 つも持たない**（ソース走査で固定） |
| 「**ロジックは TypeScript**」 | 機能分岐・PS 走査・ニーモニック・`rc` の決定はすべて `packages/server` |

**「薄い」を散文で約束せず、機械で固定した**のがこの作業の要点。
`hllapi-bridge-thinness.test.ts` が機能名・機能番号での分岐・可変の状態・外部依存・
戻り値の定数の数を検査する。**一度許すと次の人が 2 つ目を足す**類の規約なので、
検査に落とす価値がある。

### 層をまたぐ確認

| 観点 | 結果 |
|---|---|
| 依存の向き | `crates/hllapi → HTTP → packages/server → SessionManager`。逆流なし |
| **外部依存を足していない** | Rust は `std` のみ。TypeScript も新規パッケージなし（CP932 表は `TextDecoder` から組む） |
| 既存の認可を迂回していない | **`assertWritable` / `assertKeyAllowed` を通す**（01 の must で塞いだ）。<br>読み取り専用セッションへ HLLAPI から書けない |
| 秘密の扱い | バッファの中身をログに出さない。**サインオン画面への入力が通る経路**なので必須 |
| 上限 | `data` 8KB、Wait / Pause 30 秒、HTTP 45 秒。**無限に待たない** |
| 一次資料に基づく | 機能番号・戻り値・ニーモニックの出所（SunLink EHLLAPI Programmer's Manual）を明記 |
| **推測で番号を置かない** | `Start Host Notification` は目次に誤植があり確定できないので**入れていない** |
| 既存の非退行 | ルート登録 1 行のみ。3,846 件緑 |
| この環境固有の回避策 | **リポジトリに焼き込んでいない**（`.cargo/config.toml` を置かず環境変数で渡す） |

### 設計判断の妥当性（振り返り）

- **1 呼び出し = HTTP 1 往復**——同期 API を非同期サーバーへ写す最も単純な形。
  Rust に相関も接続プールも要らず、「状態を持たない」を構造で担保できた。
  実機で**別プロセスから叩き直せる**ことも確認した。
- **CP932 を選んだのは正しかった。** UTF-8 のままだと日本語画面が 1920 バイトの器に収まらず、
  既存資産の前提を壊していた。実機で `バイト=1920 セル=1920` を確認。
- **PS をバイト配列で扱う**のは、CP932 を選んだ結果として必然だった。
  文字列で持っていたときに `サイン・オン` が `サ イ ン ・ オ ン` になり、
  **日本語で検索できない**という致命的な欠陥が出ていた（02 の must）。

### 残る弱点（`test-result.md` にも記載）

- **Windows でビルドも動作確認もしていない。** 実利用者はほぼ Windows なので、
  **これが最大の未検証点**。クレートは OS 非依存に書いてあるが動作は主張しない。
- **実際の HLLAPI 資産で試していない**（手元に無い）。
- 未実装が 15 機能ある（`rc=10` で断る）。
- 画面を書き換えるローカル操作（Erase EOF 等）はカーソルを動かすだけ。

いずれも「できた」と書いていないので**この作業としては通過**とし、follow-up に送る。

### 判定

**通過。** subtask で must 3 件・should 2 件を潰し、統合 test で `Send Key` の疑いも
実機で切り分けた（製品側の欠陥ではなく検証側のキー選択の誤り）。
