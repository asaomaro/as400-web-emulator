## 受け入れ基準との対応

| 基準 | 結果 |
|---|---|
| 中核の機能が動く | **20 機能を実装、うち主要なものを実機で確認** |
| **本物の C ABI で叩いて動く** | Python `ctypes` で共有ライブラリを動的リンク（HLLAPI と同じ呼び出し規約） |
| **実機のセッション**で一連の操作が通る | Connect → 読み出し → 検索 → キー送信 → 切断まで成立 |

| Rust が状態を持たない | ソース走査で固定＋**実機で別プロセスから叩き直せることを確認** |
| 既存の非退行 | ルート登録 1 行のみ。3,846 件緑 |
| ビルド・lint・テスト | すべて緑 |

## 統合 test で切り分けたこと

**`Send Key` が「rc=0 なのに画面が変わらない」**と出たので、セッションを直接見て切り分けた。

```
F1:    timedOut=false 変化=なし
F3:    timedOut=false 変化=なし
Enter: timedOut=false 変化=あり
```

→ **AID は正しく届いている。** サインオン画面が F1 / F3 を無視するだけだった。
検証側が「効かないキー」を選んでいたのが原因で、製品側の欠陥ではない。
Enter に変えて確認した（欄は空のまま送るので**サインオンは試行されない**）。

## 測っていないこと（正直に残す）

- **Windows でビルドも動作確認もしていない。** 開発環境に MSVC / mingw が無い。
  **HLLAPI の実利用者はほぼ Windows なので、ここが最大の未検証点。**
  クレートは OS 非依存（`std::net` のみ）に書いてあるが、動作は主張しない。
- **実際の HLLAPI 資産（VB 等）で試していない。** 手元に資産が無い。
- `cargo test` をこの環境で走らせていない（`crt1.o` が無い）。
  ただし**検査の中身は共有ライブラリ経由で全部走らせた**（同じ関数）。
  薄さの検査は `npm test` 側へ移したので走っている。
- `Wait` / `Pause` の実挙動（時間依存なので偽物で検証）。
- **未実装の 15 機能**（Set Session Parameters・Copy OIA・キーストローク傍受・ファイル転送など）。
